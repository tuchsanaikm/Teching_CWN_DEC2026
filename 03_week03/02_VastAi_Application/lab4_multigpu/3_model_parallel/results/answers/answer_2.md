# สรุปผล Lab 4 · Model Parallelism — Qwen3-8B + LoRA (Text-to-SQL)

งานรันครบทุกขั้น: eval Base → หา batch → เทรน 3 Epoch → eval หลังแต่ละ Epoch โดย batch ใหญ่สุดที่ได้คือ **8** และ Exact Match ขึ้นจาก 0% เป็น 77%

เครื่อง RTX 3090 24 GB × 2 (instance <id> ป้าย `vapp-lab4-mp`) ใช้ชุดข้อมูล b-mc2/sql-create-context แบ่ง Train 4,000 และ Test 200 ตัวอย่าง

## Layer ไหนอยู่ใบไหน

| GPU | ส่วนของโมเดล | น้ำหนัก |
|---|---|---|
| GPU 0 | embed_tokens + Layer 0–17 (18 ชั้น) | 8.19 GB |
| GPU 1 | Layer 18–35 (18 ชั้น) + norm + lm_head | 8.19 GB |

## loss และ Exact Match (Test Set 200 ตัวอย่าง)

| โมเดล | train loss | test loss | Exact Match | EM แบบผ่อนปรน |
|---|---|---|---|---|
| Base | – | 1.914 | 0.0% (0/200) | 54.5% |
| Epoch 1 | 0.0876 | 0.0580 | 70.0% (140/200) | 72.5% |
| Epoch 2 | 0.0305 | 0.0506 | 77.5% (155/200) | 79.5% |
| Epoch 3 | 0.0168 | 0.0529 | 77.0% (154/200) | 79.5% |

- **Exact Match** คือข้อความตรงกับเฉลยทุกตัวอักษร ยุบเฉพาะช่องว่าง
- **แบบผ่อนปรน** ไม่สนตัวพิมพ์ ชนิดเครื่องหมายคำพูด และ `;` ท้าย ผมเพิ่มคอลัมน์นี้เองเพราะ Base ได้ 0% แบบเข้มจากการใช้ `'...'` และตัวพิมพ์ใหญ่ ต่างจากเฉลยที่ใช้ `"..."` ตัวพิมพ์เล็ก
- **train loss** คือค่าเฉลี่ยของทุก step ใน Epoch นั้น
- Epoch 3 ไม่ดีกว่า Epoch 2: train loss ยังลดลง แต่ test loss เริ่มขยับขึ้น

## ข้อสังเกต

- **GPU 1 เต็มก่อน:** logits ขนาด vocab 151,936 และการคิด loss อยู่ที่ใบนี้ จึงใช้ VRAM มากกว่า GPU 0
- **util ราว 50% ต่อใบ:** สองใบทำงานสลับกัน (forward 0→1, backward 1→0) ไม่ได้ทำพร้อมกัน
- **VRAM ตอนเทรนจริงสูงกว่าตอนหา batch:** nvidia-smi เห็นสูงสุด 18,640 / 23,826 MiB (GPU 1 เกือบเต็ม 24 GB ใน Epoch 1) ขณะที่ PyTorch ใช้จริงสูงสุด 14,630 / 17,674 MiB

## สิ่งที่ผมเลือกเองนอกค่าที่ตรึง

- learning rate ลดแบบ linear จาก 2e-4 ถึง 0, AdamW, ตัด gradient ที่ 1.0
- คิด loss เฉพาะส่วนคำตอบ SQL
- ตัวอย่าง Train 1 รายการยาว 320 token ถูกตัดเหลือ 256
