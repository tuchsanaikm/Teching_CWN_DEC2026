## สรุปผล: Round Robin เทียบ Least Connections (ระบบแบบที่ 4: GPU 2 ใบ × 4 server, Micro-batching)

วัดครบทั้ง 3 รอบ (`lc_equal`, `rr_slow`, `lc_slow`) และเปิดระบบกลับเป็น Round Robin แบบไม่หน่วงแล้ว Least Connections ได้ความจุมากกว่าทั้งสองกรณี

เกณฑ์ผ่าน = p95 ไม่เกิน 500 ms และ error ต่ำกว่า 1% ค่าสัดส่วนคำขอและ GPU ทำงานเป็น gpu0 / gpu1 วัดที่ระดับความจุ

### ตารางที่ 1: GPU เร็วเท่ากัน

| วิธี | ผล | ความจุ (N) | Throughput สูงสุด | p95 ที่ความจุ | สัดส่วนคำขอ | GPU ทำงาน |
|---|---|---|---|---|---|---|
| Round Robin | gpu2 (ผลเดิม) | 180 | 566.5 req/s (N=512) | 490.3 ms | 50.0% / 50.0% | 85% / 83% |
| Least Connections | lc_equal | 250 | 561.1 req/s (N=512) | 493.3 ms | 49.8% / 50.2% | 82% / 83% |

### ตารางที่ 2: GPU ใบที่ 2 (gpu1) ช้าลง 3 เท่า

| วิธี | ผล | ความจุ (N) | Throughput สูงสุด | p95 ที่ความจุ | สัดส่วนคำขอ | GPU ทำงาน |
|---|---|---|---|---|---|---|
| Round Robin | rr_slow | 52 | 223.4 req/s (N=128) | 495.9 ms | 50.0% / 50.0% | 55% / 95% |
| Least Connections | lc_slow | 103 | 389.3 req/s (N=256) | 493.5 ms | 70.8% / 29.2% | 82% / 93% |

### ทำไมผลต่างกัน
- **GPU เท่ากัน:** Throughput สูงสุดเท่ากัน (ประมาณ 560 req/s) เพราะ GPU เต็มทั้งคู่ แต่ Least Connections ทำให้คิวของทุก server ยาวใกล้กัน ที่ N=250 ค่า p50 คือ 444 ms และ p95 คือ 493 ms จึงรับผู้ใช้ได้มากกว่าก่อน p95 จะเกิน 500 ms
- **GPU ใบที่ 2 ช้า (Round Robin):** แจกครึ่งต่อครึ่งโดยไม่ดูงานค้าง server ของ gpu1 รอคิว 160–176 ms และเรียกโมเดล 212–234 ms ส่วน gpu0 ว่าง (ทำงาน 55%, คิว 12–13 ms) ใบช้าจึงเป็นตัวกำหนด p95 ของทั้งระบบ
- **GPU ใบที่ 2 ช้า (Least Connections):** server ที่ช้ามีงานค้างมากกว่าจึงได้งานใหม่น้อยลงเอง งานไหลไป gpu0 ประมาณ 71% ทำให้ gpu0 ทำงานถึง 82% ความจุเพิ่มจาก 52 เป็น 103 และ Throughput สูงสุดจาก 223 เป็น 389 req/s

### ข้อควรรู้
- **ตัวเทียบ Round Robin แกว่งตามรอบ:** หลังเปิดระบบกลับ ผมยิงซ้ำที่ N=180 อีก 3 ครั้ง ได้ p95 392 และ 469 ms (ผ่าน) กับ 641 ms (ไม่ผ่าน) ครั้งที่ไม่ผ่านเกิดจาก NGINX พัก server หนึ่งตัว 10 วินาทีหลัง connection reset ส่วนที่ N=250 Round Robin ไม่ผ่านทั้ง 2 ครั้ง (p95 ประมาณ 700 ms) จึงยืนยันว่าต่ำกว่า Least Connections จริง
- **วิธีหน่วง:** server ของ GPU ที่เลือกเรียกโมเดลซ้ำตามจำนวนเท่า GPU จึงทำงานจริง ไม่ใช่การ sleep ทั้งหมด ตอนตรวจตรงทีละ server ที่ N=8 ได้ 109.7 เทียบ 52.6 req/s ซึ่งไม่ถึง 3 เท่าพอดี เพราะขนาด batch ต่างกัน
- **การตั้งค่า NGINX:** ไฟล์ที่ใช้จริงของ `rr_slow` กับ `lc_slow` ต่างกันบรรทัดเดียวคือ `least_conn;`
- **ช่วงที่ไม่ได้วัด:** `lc_equal` N 251–252 และ `lc_slow` N 104–106
- **error:** `lc_equal` มี HTTP 502 หนึ่งครั้ง (0.01%) ส่วน `rr_slow` และ `lc_slow` ไม่มี error

### วิธีสั่ง
`code/cluster.sh up --gpus 2 --per-gpu 4 --mode micro --lb rr|lc [--slow-gpu G --slow-factor F]`

### สถานะเครื่อง
**เครื่อง vapp-lab6-nginx ยังเปิดอยู่ ไม่ได้ destroy** ระบบแบบที่ 4 ทำงานแบบ Round Robin ไม่มีการหน่วง (ทุก server รายงาน slowdown=1.0) และ `cluster.sh status` ขึ้น OK
