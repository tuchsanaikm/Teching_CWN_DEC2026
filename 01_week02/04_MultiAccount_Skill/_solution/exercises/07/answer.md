# แบบฝึกหัดที่ 7 · ให้ Claude อธิบายสกิลเป็นภาษาคน

ผลจากการรันจริง 1 ครั้ง ผลของแต่ละคนจะต่างกันไปตามบัญชี รุ่น และวันที่รัน

## พรอมต์

```text
อ่านคู่มือของสกิล agent-team จากใน container multi-account แล้วอธิบายให้คนที่ไม่เคยใช้เข้าใจ อ่านอย่างเดียว ไม่ต้องสั่งงานบัญชีใด
1. สกิลนี้ทำอะไรได้บ้าง เขียนเป็นรายการ ข้อละ 1 บรรทัด
2. ยกตัวอย่างประโยคภาษาคนที่ผมพิมพ์สั่งได้ ข้อละ 1 ประโยค
3. บอกสิ่งที่สกิลไม่ทำให้ และข้อควรระวัง
สรุปเป็นตาราง: ความสามารถ | ตัวอย่างประโยคสั่ง | ข้อควรระวัง
```

## คำตอบของ Claude

ผมอ่านคู่มือจาก container `multi-account` ที่ `/root/ai-accounts/.Claude/shared/skills/agent-team/` สองไฟล์ คือ `SKILL.md` กับ `references/details.md` ใช้แค่คำสั่งอ่านไฟล์ ไม่ได้สั่งงานบัญชีไหนเลย

## สกิลนี้คืออะไร (สรุปสั้น)
สกิลนี้ให้บัญชี AI หลายบัญชีจาก 3 ค่ายทำงานเป็นทีมเดียวกันได้ คือ Claude (`yolo1..5`), Codex (`cyolo1..5`) และ Gemini/Antigravity (`gyolo1..5`) คุณบอกเป็นภาษาคน แล้ว Claude จะแปลงเป็น "กราฟงาน" ซึ่งเป็นไฟล์ JSON ที่ระบุว่ามีงานอะไร ใครทำ และงานไหนต้องรองานไหน จากนั้นสคริปต์จะส่งงานให้แต่ละบัญชี ตรวจผล ย้ายงานเมื่อโควตาหมด และสรุปผลพร้อมสถิติให้

## 1–2. ความสามารถและตัวอย่างประโยคสั่ง (รวมกับข้อควรระวังในตารางเดียว)

|---|---|---|---|
| 1 | ส่งต่องานเป็นทอด (relay / DAG) โดยงานหลังรอผลงานก่อน | "ให้ Claude เขียนโค้ด แล้วส่งต่อให้ Codex เขียนเทสต์ แล้วให้ Gemini รันเทสต์" | ถ้างานไหนล้ม งานที่รอมันอยู่จะถูกบล็อกทั้งสาย |
| 2 | แบ่งงานทำพร้อมกันแล้วค่อยรวมผล (fan-out / fan-in) | "แบ่ง 3 บัญชีไปหาข้อมูลคนละหัวข้อพร้อมกัน แล้วให้อีกตัวรวมเป็นรายงานเดียว" | ทุกบัญชีที่ทำพร้อมกันใช้โควตาจริงพร้อมกัน |
| 3 | ระบบเลือกบัญชีให้เองตามประเภทงานและโควตาที่เหลือ (router) | "งานนี้ให้ระบบเลือกบัญชีที่โควตาเหลือเยอะที่สุดเอง" | งานโค้ดหรือรีวิวจะไป Codex ก่อน งานเอกสารยาวไป Claude ก่อน ถ้าอยากได้ค่ายไหนต้องบอกชัด ๆ |
| 4 | จำกัดให้ใช้แค่บางบัญชี (`--workers`) | "ใช้แค่ yolo2, cyolo1, gyolo1 ห้ามแตะบัญชีอื่น" | ถ้าบัญชีที่เลือกไม่พร้อมหมด งานจะล้ม ระบบไม่ไปยืมบัญชีอื่นมาแทน |
| 5 | ดูแผนก่อนโดยไม่เรียกโมเดลจริง (`--dry-run`) | "ขอดูแผนก่อนว่าจะแบ่งงานให้ใครบ้าง ยังไม่ต้องรันจริง" | แผนจริงอาจต่างไปบ้าง เพราะต้องดูโควตา ณ ตอนที่รัน |
| 6 | ตรวจรูปแบบผลก่อนส่งต่อ (`expect`: number, json, regex ฯลฯ) | "ให้คำตอบเป็นตัวเลขอย่างเดียว ถ้าไม่ใช่ตัวเลขถือว่าล้ม" | ถ้าผลผิดรูปแบบ งานได้สถานะ `bad_output` และงานต่อไปไม่เดิน |
| 7 | วนรีวิวจนผ่าน (review loop) | "ให้ Codex เขียน แล้วให้ Gemini ตรวจ วนแก้ไม่เกิน 3 รอบจนกว่าจะ APPROVED" | ทุกรอบเสียโควตาทั้งคนเขียนและคนตรวจ |
| 8 | ให้โต้แย้งกันแล้วมีกรรมการตัดสิน (debate) | "ให้ Claude กับ Gemini เถียงกันว่าควรใช้ฐานข้อมูลแบบไหน แล้วให้ Codex ตัดสิน" | กรรมการก็เป็น AI จึงควรดูเหตุผลที่ให้มาด้วย |
| 9 | ทำหลายเวอร์ชันแล้วเลือกอันที่ดีที่สุด (best-of-N) | "ให้ 3 ค่ายเขียนคำโปรยสินค้าคนละแบบ แล้วเลือกอันที่ดีที่สุด" | ใช้โควตาประมาณ N เท่าของการทำครั้งเดียว |

## 3. สิ่งที่สกิลไม่ทำให้ และข้อควรระวังรวม

**สิ่งที่ไม่ทำ**
- ไม่ย้ายงานที่เจาะจงบัญชี เช่น ถ้าระบุ `gyolo1` แล้ว gyolo1 ใช้ไม่ได้ งานจะล้มพร้อมบอกเหตุผล
- ไม่หยุดงานที่กำลังรันอยู่ เมื่อบัญชีหยุดรับงาน ระบบย้ายเฉพาะงานที่ยังรอคิว
- ไม่ใช้ Claude สร้างภาพ ภาพสร้างโดย Codex หรือ Gemini เท่านั้น
- ไม่เอาผลลัพธ์ของ AI ไปรันเป็นคำสั่ง shell (ห้าม `eval`)
- ไม่เก็บข้อความ prompt หรือรหัสลับลงบันทึกสถิติ เก็บแค่ตัวเลข
- ไม่เลือก Gemini เป็นหัวหน้าทีมเอง ต้องสั่งระบุ

**ข้อควรระวัง**
- **เสียโควตาจริงทุกครั้ง** ถ้ายังไม่แน่ใจให้ใช้ `--dry-run` หรือตัวจำลอง (`--simulate-limit`) ก่อน
- **ความยากระดับ 6 ฝั่ง Claude ใช้รุ่น fable** ซึ่งแพงประมาณ 2 เท่าของ opus และมีโควตารายสัปดาห์แยก
- **ภาษาไทยใน PowerShell 5.1 จะกลายเป็น `?`** ตอนส่งผ่าน pipe ให้ใช้ PowerShell 7 หรือ Git Bash แทน
- **ข้อมูลยาวให้ส่งเป็นไฟล์ (`{{file:id}}`)** ถ้าส่งผลของงานก่อนหน้าเป็นข้อความตรง ๆ (`{{id}}`) แล้วยาวเกิน 2000 ตัวอักษร ระบบจะตัดแล้วให้ไปอ่านไฟล์แทน
- **ผลทุกอย่างเก็บไว้ที่** `/workspace/.agent-team/<run_id>/` (ผลงาน กระดาน ข้อความ สถานะ) ตามไปตรวจย้อนหลังได้

ถ้าอยากลองแบบไม่เสียโควตา ประโยคที่เริ่มได้เลยคือ "ขอดูโควตาของทุกบัญชี" หรือ "วางแผนให้ดูแบบ dry-run ก่อน"
